## ADDED Requirements

### Requirement: List topics
The system SHALL expose the known topics via `GET /api/v1/topics`, responding `200` with a JSON array of topic name strings. The list comes from the active storage backend (the vault registry in Obsidian mode; a seeded list in memory mode) and SHALL NOT be hardcoded in route or service code. Tasks MAY have no topic — the list is the set of allowed values when one is supplied.

#### Scenario: Topics listed
- **WHEN** a client sends `GET /api/v1/topics`
- **THEN** the response is `200` with a JSON array of the storage backend's known topic names

#### Scenario: Registry drives the API in Obsidian mode
- **WHEN** the service runs in Obsidian mode and a topic is added to the vault's registry note
- **THEN** a subsequent `GET /api/v1/topics` includes it without a service restart

## MODIFIED Requirements

### Requirement: Task representation
The system SHALL represent a task with the following attributes: `id` (opaque string, generated by the system, unique per task), `title` (non-blank string, required), `dueDate` (optional, ISO-8601 date `yyyy-MM-dd`, no time component), `topic` (optional; when present, one of the known topics — see List topics), and `done` (boolean). Clients MUST NOT be able to supply or change `id`; request bodies containing unknown fields (including `id` and the former `category`/`completed` names) SHALL be rejected with `400`.

#### Scenario: Task serialized with all attributes
- **WHEN** a task is returned by any endpoint
- **THEN** the JSON body contains `id`, `title`, `done`, and — when set — `dueDate` (as `yyyy-MM-dd`) and `topic`

#### Scenario: Id is system-generated
- **WHEN** a client creates a task
- **THEN** the system generates the `id`

#### Scenario: Client-supplied id rejected
- **WHEN** a client sends `POST /api/v1/tasks` with an `id` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Former field names rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a `category` or `completed` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

### Requirement: Create task
The system SHALL allow creating a task via `POST /api/v1/tasks` with a JSON body containing `title` (required), and optionally `dueDate`, `topic`, and `done`. When `done` is omitted it MUST default to `false`. A supplied `topic` MUST be one of the known topics (see List topics); an unknown topic SHALL be rejected with `400` and a JSON error body containing a `message`. On success the system SHALL respond `201 Created` with the full task representation including its generated `id`.

#### Scenario: Create with only a title
- **WHEN** a client sends `POST /api/v1/tasks` with body `{"title": "Pay rent"}`
- **THEN** the response is `201` with a task having a generated `id`, `title` "Pay rent", no `dueDate`, no `topic`, and `done` `false`

#### Scenario: Create with all fields
- **WHEN** a client sends `POST /api/v1/tasks` with `title`, `dueDate`, and `topic` set
- **THEN** the response is `201` and the returned task contains the submitted values

#### Scenario: Create with blank title rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a missing or blank `title`
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Create with unknown topic rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a `topic` that is not in the known-topics list
- **THEN** the response is `400` with a JSON error body containing a `message` and no task is created

### Requirement: List tasks
The system SHALL return all stored tasks via `GET /api/v1/tasks` as a JSON array with status `200`. When the optional query parameter `topic` is provided, the system SHALL return only tasks whose `topic` equals the given value exactly.

#### Scenario: List all tasks
- **WHEN** a client sends `GET /api/v1/tasks` and two tasks exist
- **THEN** the response is `200` with a JSON array containing both tasks

#### Scenario: List is empty
- **WHEN** a client sends `GET /api/v1/tasks` and no tasks exist
- **THEN** the response is `200` with an empty JSON array

#### Scenario: Filter by topic
- **WHEN** a client sends `GET /api/v1/tasks?topic=home` and tasks with topics "home" and "family" exist
- **THEN** the response contains only the tasks with topic "home"

### Requirement: Update task
The system SHALL replace an existing task via `PUT /api/v1/tasks/{id}` with the same body schema and topic validation as create (full replace: fields omitted from the body are unset, except `done` which defaults to `false`). The task's `id` MUST remain unchanged. On success the system SHALL respond `200` with the updated task. When the active storage backend does not support updates (Obsidian mode), the system SHALL respond `501` with a JSON error body containing a `message` explaining the operation is not yet supported.

#### Scenario: Update replaces all fields
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` for an existing task with a body containing a new `title` and no `topic`
- **THEN** the response is `200`, the task has the new `title`, its `topic` is unset, and its `id` is unchanged

#### Scenario: Mark task as done
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with `done` set to `true`
- **THEN** the response is `200` and the returned task has `done` `true`

#### Scenario: Update unknown task
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with an id that does not exist
- **THEN** the response is `404` with a JSON error body containing a `message`

#### Scenario: Update with invalid body rejected
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with a missing or blank `title`
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Update unsupported in Obsidian mode
- **WHEN** the service runs with Obsidian storage and a client sends `PUT /api/v1/tasks/{id}`
- **THEN** the response is `501` with a JSON error body containing a `message`, and no vault content changes

### Requirement: Delete task
The system SHALL delete a task via `DELETE /api/v1/tasks/{id}`, responding `204 No Content` on success. Subsequent reads of the deleted id MUST return `404`. When the active storage backend does not support deletion (Obsidian mode), the system SHALL respond `501` with a JSON error body containing a `message` explaining the operation is not yet supported.

#### Scenario: Delete existing task
- **WHEN** a client sends `DELETE /api/v1/tasks/{id}` for an existing task
- **THEN** the response is `204` and a subsequent `GET /api/v1/tasks/{id}` returns `404`

#### Scenario: Delete unknown task
- **WHEN** a client sends `DELETE /api/v1/tasks/{id}` with an id that does not exist
- **THEN** the response is `404` with a JSON error body containing a `message`

#### Scenario: Delete unsupported in Obsidian mode
- **WHEN** the service runs with Obsidian storage and a client sends `DELETE /api/v1/tasks/{id}`
- **THEN** the response is `501` with a JSON error body containing a `message`, and no vault content changes
