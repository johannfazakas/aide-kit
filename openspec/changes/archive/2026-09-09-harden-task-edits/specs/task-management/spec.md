# Delta: task-management

## MODIFIED Requirements

### Requirement: Task representation
The system SHALL represent a task with the following attributes: `id` (opaque string, generated by the system, unique per task), `title` (non-blank single-line string, required — line breaks and other control characters SHALL be rejected with `400`), `dueDate` (optional, ISO-8601 date `yyyy-MM-dd`, no time component), `topic` (optional; when present, one of the known topics — see List topics), and `done` (boolean). Task responses additionally carry `revision`, an opaque storage revision current at the time the task was read (see Optimistic concurrency via storage revision). Clients MUST NOT be able to supply or change `id`; request bodies containing unknown fields (including `id` and the former `category`/`completed` names) SHALL be rejected with `400`.

#### Scenario: Task serialized with all attributes
- **WHEN** a task is returned by any endpoint
- **THEN** the JSON body contains `id`, `title`, `done`, `revision`, and — when set — `dueDate` (as `yyyy-MM-dd`) and `topic`

#### Scenario: Id is system-generated
- **WHEN** a client creates a task
- **THEN** the system generates the `id`

#### Scenario: Client-supplied id rejected
- **WHEN** a client sends `POST /api/v1/tasks` with an `id` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Former field names rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a `category` or `completed` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Multi-line title rejected
- **WHEN** a client sends a create, update, or rename with a `title` containing a line break
- **THEN** the response is `400` with a JSON error body containing a `message` and nothing is stored

## ADDED Requirements

### Requirement: Optimistic concurrency via storage revision
The system SHALL expose an opaque, monotonically advancing storage revision so callers can detect that the store changed between their read and their mutation. Every task response (create, get, list elements, and mutation results) SHALL carry the revision current when it was produced; every mutation request (`PUT /tasks/{id}`, the intent endpoints, and `DELETE`) SHALL accept an optional `revision`. When a supplied revision is not the store's current revision, the mutation SHALL fail with `409` and a JSON error body whose `message` states the store has changed and the caller should re-read; nothing is written. When the revision is omitted the mutation proceeds without the staleness check. A successful mutation response SHALL carry the new revision, so sequential edits can chain without re-listing. In Obsidian mode the revision reflects the vault clone's synchronized state; the in-memory backend advances a counter on every mutation.

#### Scenario: Stale revision rejected
- **WHEN** a client reads a task, the store is changed by another writer, and the client sends `POST /api/v1/tasks/{id}/complete` carrying the old revision
- **THEN** the response is `409` with a JSON error body containing a `message`, and the task is unchanged

#### Scenario: Current revision accepted
- **WHEN** a client sends a mutation carrying the revision from its most recent read and no other write happened since
- **THEN** the mutation succeeds and the response carries a newer revision

#### Scenario: Chained edits without re-listing
- **WHEN** a client applies two mutations in sequence, passing each response's revision into the next request
- **THEN** both succeed without any intermediate list or get

#### Scenario: Revision omitted
- **WHEN** a client sends a mutation without a `revision`
- **THEN** the mutation proceeds exactly as before the revision mechanism existed
