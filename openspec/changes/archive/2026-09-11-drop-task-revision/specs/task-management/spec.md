# task-management (delta)

## MODIFIED Requirements

### Requirement: Task representation
The system SHALL represent a task with the following attributes: `id` (opaque string, generated by the system, unique per task), `title` (non-blank single-line string, required — line breaks and other control characters SHALL be rejected with `400`), `dueDate` (optional, ISO-8601 date `yyyy-MM-dd`, no time component), `topic` (optional; when present, one of the known topics — see List topics), and `done` (boolean). Clients MUST NOT be able to supply or change `id`; request bodies containing unknown fields (including `id` and the former `category`/`completed` names) SHALL be rejected with `400`.

#### Scenario: Task serialized with all attributes
- **WHEN** a task is returned by any endpoint
- **THEN** the JSON body contains `id`, `title`, `done`, and — when set — `dueDate` (as `yyyy-MM-dd`) and `topic`

#### Scenario: Id is system-generated
- **WHEN** a client creates a task
- **THEN** the system generates the `id`

#### Scenario: Client-supplied id rejected
- **WHEN** a client sends `POST /api/v1/tasks` with an `id` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Former field names rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a `category` or `completed` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Multi-line title rejected
- **WHEN** a client sends a create, update, or rename with a `title` containing a line break
- **THEN** the response is `400` with a JSON error body containing a `message` and nothing is stored

## REMOVED Requirements

### Requirement: Optimistic concurrency via storage revision
**Reason**: This is a single-user application backed by a git vault; the storage-revision token added pervasive complexity across every layer for marginal value. The per-field patch merged onto freshly-pulled state already prevents concurrent edits to *different* fields from clobbering each other, and a same-field overwrite is recoverable from git history.
**Migration**: Mutation requests (`PUT /tasks/{id}`, the intent endpoints, `DELETE`) no longer accept or return a `revision`; existing callers simply omit it. Mutations are last-writer-wins on the named field. The git rebase/push conflict path (a `409` vault conflict in Obsidian mode) is unchanged.
