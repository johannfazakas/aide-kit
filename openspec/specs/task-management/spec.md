# Spec: task-management

## Purpose

Manage tasks through a CRUD HTTP API: create, list, fetch, update, and delete tasks with optional due dates and categories.

## Requirements

### Requirement: Task representation
The system SHALL represent a task with the following attributes: `id` (opaque string, generated by the system, unique per task), `title` (non-blank string, required), `dueDate` (optional, ISO-8601 date `yyyy-MM-dd`, no time component), `category` (optional, free-form string), and `completed` (boolean). Clients MUST NOT be able to supply or change `id`; request bodies containing unknown fields (including `id`) SHALL be rejected with `400`.

#### Scenario: Task serialized with all attributes
- **WHEN** a task is returned by any endpoint
- **THEN** the JSON body contains `id`, `title`, `completed`, and — when set — `dueDate` (as `yyyy-MM-dd`) and `category`

#### Scenario: Id is system-generated
- **WHEN** a client creates a task
- **THEN** the system generates the `id`

#### Scenario: Client-supplied id rejected
- **WHEN** a client sends `POST /api/v1/tasks` with an `id` field in the body
- **THEN** the response is `400` with a JSON error body containing a `message`

### Requirement: Create task
The system SHALL allow creating a task via `POST /api/v1/tasks` with a JSON body containing `title` (required), and optionally `dueDate`, `category`, and `completed`. When `completed` is omitted it MUST default to `false`. On success the system SHALL respond `201 Created` with the full task representation including its generated `id`.

#### Scenario: Create with only a title
- **WHEN** a client sends `POST /api/v1/tasks` with body `{"title": "Pay rent"}`
- **THEN** the response is `201` with a task having a generated `id`, `title` "Pay rent", no `dueDate`, no `category`, and `completed` `false`

#### Scenario: Create with all fields
- **WHEN** a client sends `POST /api/v1/tasks` with `title`, `dueDate`, and `category` set
- **THEN** the response is `201` and the returned task contains the submitted values

#### Scenario: Create with blank title rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a missing or blank `title`
- **THEN** the response is `400` with a JSON error body containing a `message`

### Requirement: List tasks
The system SHALL return all stored tasks via `GET /api/v1/tasks` as a JSON array with status `200`. When the optional query parameter `category` is provided, the system SHALL return only tasks whose `category` equals the given value exactly.

#### Scenario: List all tasks
- **WHEN** a client sends `GET /api/v1/tasks` and two tasks exist
- **THEN** the response is `200` with a JSON array containing both tasks

#### Scenario: List is empty
- **WHEN** a client sends `GET /api/v1/tasks` and no tasks exist
- **THEN** the response is `200` with an empty JSON array

#### Scenario: Filter by category
- **WHEN** a client sends `GET /api/v1/tasks?category=work` and tasks with categories "work" and "home" exist
- **THEN** the response contains only the tasks with category "work"

### Requirement: Get task by id
The system SHALL return a single task via `GET /api/v1/tasks/{id}` with status `200` when a task with the given id exists.

#### Scenario: Get existing task
- **WHEN** a client sends `GET /api/v1/tasks/{id}` for an existing task
- **THEN** the response is `200` with that task's full representation

#### Scenario: Get unknown task
- **WHEN** a client sends `GET /api/v1/tasks/{id}` with an id that does not exist
- **THEN** the response is `404` with a JSON error body containing a `message`

### Requirement: Update task
The system SHALL replace an existing task via `PUT /api/v1/tasks/{id}` with the same body schema as create (full replace: fields omitted from the body are unset, except `completed` which defaults to `false`). The task's `id` MUST remain unchanged. On success the system SHALL respond `200` with the updated task.

#### Scenario: Update replaces all fields
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` for an existing task with a body containing a new `title` and no `category`
- **THEN** the response is `200`, the task has the new `title`, its `category` is unset, and its `id` is unchanged

#### Scenario: Mark task as completed
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with `completed` set to `true`
- **THEN** the response is `200` and the returned task has `completed` `true`

#### Scenario: Update unknown task
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with an id that does not exist
- **THEN** the response is `404` with a JSON error body containing a `message`

#### Scenario: Update with invalid body rejected
- **WHEN** a client sends `PUT /api/v1/tasks/{id}` with a missing or blank `title`
- **THEN** the response is `400` with a JSON error body containing a `message`

### Requirement: Delete task
The system SHALL delete a task via `DELETE /api/v1/tasks/{id}`, responding `204 No Content` on success. Subsequent reads of the deleted id MUST return `404`.

#### Scenario: Delete existing task
- **WHEN** a client sends `DELETE /api/v1/tasks/{id}` for an existing task
- **THEN** the response is `204` and a subsequent `GET /api/v1/tasks/{id}` returns `404`

#### Scenario: Delete unknown task
- **WHEN** a client sends `DELETE /api/v1/tasks/{id}` with an id that does not exist
- **THEN** the response is `404` with a JSON error body containing a `message`

### Requirement: Malformed requests
The system SHALL respond `400` with a JSON error body containing a `message` when a request body is not valid JSON or does not match the expected schema (e.g., invalid `dueDate` format).

#### Scenario: Malformed JSON rejected
- **WHEN** a client sends `POST /api/v1/tasks` with a body that is not valid JSON
- **THEN** the response is `400` with a JSON error body containing a `message`

#### Scenario: Invalid due date rejected
- **WHEN** a client sends `POST /api/v1/tasks` with `dueDate` "next tuesday"
- **THEN** the response is `400` with a JSON error body containing a `message`
